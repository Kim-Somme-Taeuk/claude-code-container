# Primary Goals

Run Claude Code in isolated containers with:

1. **Per-project isolation** — containers named by path hash, each project gets its own environment
2. **Runtime-agnostic container execution** — works with Docker or Podman; auto-detect with Podman preferred, override via `--runtime` / `CCC_RUNTIME`. First-class support for rootless Podman on Linux and podman machine on macOS/Windows (added 2026-04-17)
3. **Host environment forwarding** — auto-forward env vars, SSH agent, locale, timezone
4. **Session lifecycle management** — lock files track sessions, auto-stop container when last session exits
5. **Tool version management** — mise-based per-project tool versions
6. **Browser testing** — Chromium included for headless testing
7. **Network transparency** — `--network host` for direct port access, localhost proxy for Docker Desktop / podman machine
8. **Tool credential availability** — every local container mounts all registered coding-tool credential directories regardless of the command or tool that starts it
9. **Shared Codex config access** — before host MCP generation and after command exit, recover host read/write access to a regular config in a real caller-owned credential directory. Preserve file UID/GID, content and unrelated effective permissions. When host/container UIDs differ, grant narrowly scoped file ACL access to both mapped principals instead of transferring ownership. Derive the host principal from the mounted parent inside the container. Reject unsafe paths, invalid identities, malformed ACLs and mask expansion that would expose unrelated rights. Unsupported ACL operations must not fall back to broadening mode bits. Host recovery failure warns; unresolved MCP access fails explicitly. Recheck at CCC boundaries after external atomic replacement; arbitrary concurrent replacement/content editing is not synchronized.
10. **Requested coding-tool installation and direct execution** — cold and warm Codex startup ensures only Codex, without probing/installing Gemini or OpenCode. The npm installer retains independent transactions when explicitly ensuring multiple tools. Requested-tool readiness, install and wrapper failures preserve their cause and clean up. Execute the requested command once, preserve its numeric status and inherited output, and clean up session/environment state. Generic failures must not trigger forced updates, destructive state-wipe prompts, retries or credential/history/plugin deletion.

11. **Writable Codex authentication storage** — at Codex session startup, verify that its container user can read, write and traverse the mounted credential directory as well as access the config. For an inaccessible real directory owned by the invoking host user with ordinary Unix permissions, grant only the actual container user a named-user access ACL on that directory. During the directory ACL grant, preserve directory ownership, existing group/other effective access, and child contents/permissions; do not apply recursive or default ACL changes. Leave healthy directories unchanged and decline unsafe paths or complex existing ACLs. Include the ACL utilities in images and provision them on demand in older containers. Any preparation or verification failure must stop before launching Codex, preserve the cause, and clean the session and temporary environment file. A successful login must be able to save authentication state when host and container UIDs differ.

Verification: permission regression tests exercise actual EACCES on a temporary config where Unix permissions apply, recovery before MCP merging, and preservation of user settings. Installer and startup tests cover optional failures, active failures, directory access, safe ACL repair, rejected repair, cleanup, and cold/warm recovery. Real Docker tests use disposable credentials and a synthetic API key to verify authentication storage without an external account login. Mocked runtime evidence alone does not establish WSL2 Docker Desktop integration; actual container checks require a reachable runtime.

12. **Automatic Codex Harness bootstrap** — on Codex commands, install the canonical Harness Codex runtime when no Harness configuration exists, using the same default container user as credential preparation and Codex, including when runtime UID mapping overrides the image user. Use the pinned official source, persist installation in the existing Codex home, and reuse registered payload without network on subsequent starts or container recreation. Preserve explicit disabled/custom Harness settings and unrelated configuration; diagnose incomplete existing installations without forcing replacement. Serialize bootstrap and CCC Codex MCP configuration writes across projects. Reject nested CCC configuration mutation from inside a container before entering the operation, directing the caller to the host shell, because nested callers cannot share the host lock namespace. Never automatically reclaim stale or malformed Codex locks; fail before modifying the contested record and identify the lock path plus safe manual recovery after other CCC sessions close. MCP configuration failures must clean up the starting session and preserve the original error on cold and warm paths. Bound installation waits, restore host config access before releasing the bootstrap lock, and report optional installation failure while retaining Codex availability. Do not initialize project Harness files. Verify real plugin, hook, and MCP availability in an isolated container.

13. **Stable clipboard state across container restarts** — retain the existing clipboard port file and its inode during last-session stop, stale-health handling and daemon shutdown. Authenticated health determines whether its saved port/token is still usable. Publish replacement metadata through a validated regular-file descriptor without replacing the inode or following unsafe targets. Old daemon shutdown must not delete a successor's startup lock. Verify the next session can restart the same container and read fresh metadata through its existing bind mount. This does not promise an active session will follow a daemon that moves to another port. When container UID mapping makes the mounted metadata unreadable, clipboard shims must retain the valid per-session token instead of replacing it with an empty failed read.

For version upgrades, acknowledge the old server's shutdown and allow its existing bounded shutdown grace to complete before publishing successor state; failed acknowledgement must not launch a competing replacement. Serialize this entire handoff across current clients using a startup lock that legacy cleanup cannot delete; waiting clients must allow for shutdown, grace and startup, including cancellation of the first client. Legacy versions that unlink the file can cause one unavoidable inode replacement and container recreation during the first upgrade. Verify delayed legacy cleanup cannot erase successor metadata, including when the invoking CLI exits immediately after startup or overlapping startup is cancelled.

14. **Persistent npm tool recovery** — when a launcher wrapper is absent, verify the actual installed Node 22 global executable with a bounded check before restoring the wrapper. A healthy persistent package requires no npm installation or cache cleanup. Missing or unhealthy packages follow the existing independent installation path; runtime/probe infrastructure failures retain their cause. Preserve Codex-only startup and active/optional failure handling. Verify offline recreation with a persistent mise volume.

15. **Accurate proxy presence checks** — inspect the expected loopback listener and TCP LISTEN state inside the container without requiring ss or opening a connection to the transparent proxy. Keep bounded verification and actionable warnings on absence or inspection failure. Preserve existing platform/direct-reach gates. Listener presence alone does not establish host application connectivity or browser OAuth callback reachability.

16. **Honest source-image recovery** — when the requested registry image cannot be pulled, retain the existing fallback and identify how to build from a CCC source checkout. A source installation must use a genuinely built and verified image; do not relabel the old image as the new version. Preserve the previous image and persistent user storage during local replacement. Unreproduced upstream failures must remain explicitly unconfirmed rather than trigger speculative package or authentication resets.

17. **OpenCode data access before installation** — before checking a persisted OpenCode binary or installing its npm package, and when starting an already-installed active OpenCode, verify default-container-user read/write/traverse access to the mounted data root. OpenCode's version check can create data directories; an access failure can otherwise be hidden behind subsequent musl platform errors. For a real caller-owned host directory with ordinary permissions, grant only the actual container UID a named-user access ACL. Preserve owner UID/GID, existing owner/group/other effective access, and all descendants. Verify the pinned mounted directory owner matches the validated host user before mutation. Serialize inode-pinned grants, accept an identical existing grant, and reject symlinks, invalid identities, custom/default ACLs requiring changes and unsupported ACL operations without chmod/chown fallback. Healthy directories require no privileged mutation. Distinguish access denial from runtime/probe failures. An active OpenCode preparation failure stops setup with its path and cause; an optional failure warns and skips only OpenCode before cache/install mutations. Keep Codex-only startup free of OpenCode preparation. Existing inaccessible descendants and config files require manual inspection. Verify the actual npm/version failure and recovery with a disposable host-owned Docker bind mount.
