# Hyper-V snapshot journal repair through the typed library

## Scope

Device Lab reconciles an interrupted Hyper-V snapshot create, delete, or restore from its owner-scoped journal. It sends a single typed `Repair-VMSnapshotState` request to the Hyper-V Windows library before interpreting the live VM and checkpoint inventory. The request carries the exact VM ID, name, ownership Notes, expected checkpoint policy, and owner-scoped checkpoint name. Device Lab derives these values; the library does not derive CCC ownership or naming rules.

## Required behavior

- A missing or differently owned VM cannot have its checkpoint policy changed. Native code checks ID, name, and Notes at the mutation boundary and again before any quarantine change.
- A VM already set to `Disabled` is quarantined and must not be restored automatically.
- If the policy differs, native code sets the expected `Production` or `ProductionOnly` policy and verifies the result. If restoration fails, it attempts to set `Disabled` on the same owned VM and verifies that quarantine. Failed quarantine has a distinct bounded error.
- The transaction counts owner-scoped checkpoint names using Hyper-V's case-insensitive name comparison. Zero or one candidate is valid. Multiple candidates fail without choosing, deleting, or restoring a checkpoint.
- Device Lab does not replay a repair whose execution outcome is uncertain. It keeps the journal on any repair, transport, decoding, or post-repair status failure.
- After a successful typed repair, Device Lab requires complete base disk chain reads and checks the live VM identity, checkpoint policy, and snapshot inventory through its typed status path before updating tracked state or clearing the journal. The candidate count must match the repair result; a changed snapshot ID or differently cased checkpoint name retains the journal as an ownership conflict. A restore journal still requires an explicit retry for the same snapshot ID. Forced destructive VM deletion may supersede an unreconcilable snapshot journal under the existing delete policy.
- Public responses contain bounded error codes and never expose provider paths, secrets, or raw script output.
- `device_snapshot_list` compares each tracked checkpoint's exact ID and owner-scoped name with live Hyper-V status. It recognizes an untracked owner prefix without regard to case, matching the typed status filter, while retaining exact case for tracked names. On a mismatch it makes at most two additional read-only observations, 300 ms apart, within one 45-second broker deadline below the packaged MCP route's 60-second limit. It returns 409 if the inventory still differs; listing never adopts, deletes, or restores an untracked checkpoint. A follow-up read failure remains a provider or invalid-result error. The Linux Level 3 failure diagnostic records only missing and untracked counts so the next Windows host run can distinguish a transient read from persistent drift without disclosing checkpoint names or IDs.
- Snapshot create confirms that `Get-VMSnapshot` can read the exact checkpoint ID returned by `Checkpoint-VM -Passthru`, with the expected owner-scoped name and VM ID, before publishing the snapshot as tracked. Each confirmation read is cancelled at the remaining ten-second confirmation deadline, inside a 45-second create budget. A new create journal records that exact confirmation is required before mutation and records the returned ID atomically before confirmation. Unknown or absent IDs keep the journal unresolved; reconciliation of a new journal may adopt only its exact returned ID. A differently named, differently owned, or competing same-name checkpoint fails closed. Legacy journals without the confirmation flag retain their existing name-based recovery rule.

## Verification

Fake-host tests cover expected policy, restoration, pre-existing quarantine, restoration and quarantine failures, ownership drift, zero/one/duplicate candidates, uncertain transport, malformed results, journal retention, creation confirmation, and inventory retry classification. Static and package tests prove the typed request and pinned PowerShell asset ship together. A 2026-09-23 Linux Level 3 Windows-host run with a fresh v14 broker reached checkpoint listing and returned 409 with zero untracked and one missing tracked checkpoint after three reads. The diagnostic now also records the owner-inventory count, distinguishing an empty owner list from a same-ID name mismatch without disclosing checkpoint names or IDs. A v15 host run is required to observe the stronger create confirmation and determine the underlying host behavior.
